# 明日方舟 Wiki 知识问答 Agent

一个**检索增强生成（RAG）**系统：基于 PRTS Wiki 的 19,696 个页面，能回答干员数值、档案剧情、人物关系三类问题，每条结论都带可溯源的引用。

核心设计是**双轨检索**——能用 SQL 精确算出来的（"精二要几个炽合金块"）绝不交给向量去猜，只能"读懂"的（"她为什么戴头盔"）才走语义检索。

## 效果速览

以下均为系统真实输出，未做修饰（过长的回答有省略，用 …… 标出）。

### 例 1 · SQL 精确查询

```
Q: 泥岩精二需要哪些材料？
① 路由   意图=sql  实体=泥岩  依据：命中结构化词 ['精二','需要','材料']
② SQL    命中 8 行
④ 组装   SQL 8 行 · 证据 0 条 · prompt≈528 token

泥岩精二所需材料：
- 龙门币 ×180000
- 炽合金块 ×5
- 重装双芯片 ×4
- 晶体电子单元 ×4
```

数值全部来自 SQLite 精确查询，模型只做转述。系统提示词里明令**禁止重新计算或换算**——LLM 看到"5 个炽合金块"会顺手帮你换算，这条指令写与不写差别极大。

### 例 2 · 别名归一 + 共现召回

```
Q: Logos 认识泥岩吗
① 路由   意图=semantic  实体=逻各斯(Logos) / 泥岩(Mudrock)
③ 检索   4 条证据，其中 2 条为共现证据

认识。泥岩在卡兹戴尔境内与精英干员 Logos 接触，随后者前往罗德岛 [1]。
Logos 在卡兹戴尔遭遇泥岩小队时，确认对方遭莱塔尼亚势力追击、意图赶尽
杀绝后，选择出手相助 [2]。

引用  [1] 人员档案·泥岩 [共现2]   [2] 人员档案·泥岩 [共现2]
```

这是本项目**最有代表性的一次修复**。修复前，这段真证据就在库里，却因为只认中文名而被判成"无共现"，模型的回答是"资料未明确说明，无法确认"。

### 例 3 · 无据拒答

```
Q: 森西和泥岩之间有什么故事？
① 路由   意图=semantic  实体=森西 / 泥岩  资料=story
③ 检索   4 条证据  ⚠ 无共现证据，将降级为分别介绍

资料中没有记载这几位干员之间有直接互动，以下分别介绍各自的情况。
- 现有资料只涉及泥岩，未出现森西的任何档案内容。
- 泥岩在干员密录中与泥岩小队、大鲍勃有互动……
（中略）
关于森西，当前材料中没有可引用的信息，无法介绍。
```

拒答是**代码分支**，不是提示词约束。空 context 时根本不调 LLM——靠"请不要编造"拦不住幻觉，必须让代码不给它机会。

### 例 4 · 两轨融合

```
Q: 泥岩值得培养吗？
① 路由   意图=hybrid  命中复合词 ['值得','培养'] → 数值+语义两边都要
② SQL    命中 1 行（精2满级面板）
③ 检索   4 条证据

结论：值得培养，但材料只支持部分判断。
- 精2满级面板：生命 3928、攻击 882、防御 602、法抗 10 [数据表]
- 源石技艺可操纵泥土与岩石，并掌握多种莱塔尼亚古典法术 [4]
- 材料未提供技能、天赋具体数值与培养成本，无法给出精确的培养优先级建议。
```

复合问题若只走语义轨道，模型就只能凭剧情文本谈强度——那是幻觉的温床。这里强制补一条满级面板作为数值依据。

### 例 5 · 别名修复生效，但生成层仍有瑕疵

```
Q: 小羊是谁的昵称
① 路由   实体=艾雅法拉（Eyjafjalla / エイヤフィヤトラ / Eyja / 小绵羊 / 小羊）

"小羊"是艾雅法拉的昵称 [3]。
依据：晋升记录中提到，艾雅法拉昵称她的黑色绒毛宠物为"小黑羊"……
```

实体识别已经修好了（"小羊"正确归一到艾雅法拉），结论也对。但**依据引错了**：证据说的是宠物叫"小黑羊"，不是艾雅法拉本人被叫"小羊"。模型用不严谨的证据支撑了一个正确的结论。

这个案例特意保留，因为它说明两件事：路由层的确定性远高于生成层；以及为什么 L3 评测只判"引用编号是否真实存在"，而不判答案质量好坏——后者需要 LLM-as-judge 或人工，成本高且不稳定。

### 例 6 · 剧情问答（第 10 步补齐数据后新增的能力）

```
Q: 给我讲讲主线剧情第一章的大致剧情
① 路由   意图=semantic  资料=lore_main
         锁定章节「第一章 黑暗时代·下」→ 只检索该章剧情
③ 检索   4 条证据，全部来自第一章

第一章「黑暗时代·下」大致剧情：
- 罗德岛在切尔诺伯格执行营救博士的撤退行动，途中遭整合运动拦截 [2][4]。
- 1-8 中阿米娅为保护众人强行施术，设下的屏障燃烧，杜宾警告会危及她的戒指；
  临光出手去破坏塔露拉的法术，Ace 赶到劝阿米娅把重担分给大家 [1]。
- 1-10 后队伍突破拦截，杜宾与临光私下谈及牺牲者，决定不让阿米娅再受煎熬 [3]。
- 1-12 撤退最终阶段，神秘人 W 出现阻拦，自称与塔露拉合不来，目标是见博士 [2]。
```

**这个功能是"问出来才发现的"**。补齐前问同一句话，系统检索到的全是干员密录，最后回答"资料里没有主线剧情的内容"——拒答得倒是正确，但那是因为**数据范围**就没覆盖剧情。

关键设计：剧情块的 `operator` 元数据存的是**章节名**而不是角色名。这样问干员时按人过滤不会把剧情混进来（避免稀释原有检索），而章节能被精确锁定。

### 例 7 · 跨活动剧情的关系发现

```
Q: 森西和泥岩之间有什么故事？
① 路由   实体=森西 / 泥岩
③ 检索   4 条证据，其中 3 条 [共现2]

森西与泥岩的直接交集出现在罗德岛大食堂行动前：……泥岩认出此书并询问他们是
否认识大鲍勃 [3]；森西随即感叹能把坚硬虫子做成美味 [3]。
引用：[2][3][4] 支线剧情·品尝魔物  [共现2]
```

森西是《迷宫饭》联动角色，和泥岩的对话只存在于活动剧情「品尝魔物」里，**干员档案和密录里一个字都没有**。补剧情之前这个问题会被判成"无共现"从而拒答。

这条同时是下面「期望值要跟着数据更新」的由头。

## 架构

```
                        用户提问
                            │
                            ▼
              ①  Query Routing（规则，非 LLM）
                 判断走哪条轨道、认出哪些实体
                            │
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
   ② SQL 轨道                          ③ 语义轨道
   SQLite 精确查询                     三路召回 + RRF 融合
   数值、材料、排行                    ├─ dense  向量（BGE-small-zh）
   结果可验算                          ├─ sparse BM25（字符 2-gram）
                                       └─ cooc   共现（本项目特有）
        └───────────────────┬───────────────────┘
                            ▼
              ④  Augmentation（证据组装）
                 编号 [1][2]、长度预算、SQL 表格化
                 两条轨道都空 → 代码级拒答，不调 LLM
                            ▼
              ⑤  Generation（DeepSeek / OpenAI 兼容）
                            ▼
              ⑥  Citation（引用溯源）
```

**为什么路由用规则而不是 LLM**：同一个输入永远同一个输出，可以写回归测试；零延迟零成本；每个判断都能打印"因为命中了哪个词"，线上出问题能 debug。生产系统里规则路由通常吃掉 70%+ 的流量。

**为什么共现要独立成一路**：问"A 和 B 什么关系"时，答案必须在**同一段文本里同时提到两人**。纯向量检索会把"讲 A 的段落"和"讲 B 的段落"都排到前面，但那两段拼不出关系。共现路专门找"同时提到两人的块"，权重给到 1.5（dense 1.0 / sparse 0.3 / cooc 1.5）。

## 几个值得记的决策

### 1. 官方结构化元数据 > 正文文本统计

挖干员昵称时，我用正文词频挖到"小羊 → 贝娜"（贝娜档案里奶奶叫她"小羊羔"，高频）。但玩家口中的"小羊"其实是艾雅法拉。

真相在 MediaWiki 的重定向页：编辑者建一个"小羊"页面，内容只有一行 `#重定向 [[艾雅法拉]]`。**全站重定向页就是一份人工维护的官方别名表**。

而抓取时我用 `apfilterredir=nonredirects` 过滤了重定向——过滤内容是对的（不然向量库混进上万跳转空壳），但把标题也扔了，等于扔掉别名表。

教训：**选错数据源，看再多上下文也会采纳错误答案**。别名最终定为三层优先级：外文名 < 人工昵称表 < 官方重定向，冲突时官方说了算。

### 2. 叫法不一致是垂直领域 RAG 的头号召回杀手

"Logos 认识泥岩吗"这个案例最惊险的地方在于：它**不报错、不返回空结果**，只是静静地把真证据判成"无共现"，然后让模型降级回答。脚本指标完全测不出来，只有真跑问答才会暴露。

修复后共现判定改为**按实体计数而非按词计数**：一段文本同时出现"泥岩"和"Mudrock"仍算一个实体；"泥岩"+"Logos"才算两个。

### 3. 拒答必须是代码分支

空 context 时模型会调用自己的预训练知识来"补全"，那正是幻觉的定义。所以两条轨道都空时，代码直接返回固定话术，压根不调 LLM。关系类问题另有降级分支：没有共现证据时，强制模型只能分别介绍并声明"资料未记载两人有互动"。

### 4. 评测要防假绿

- **空回答判失败**：模型没说话 ≠ 说得对。否则网络抖动导致的空响应会被静默判绿。
- **打印 L3 实际调用次数**：如果是 0，说明全走拒答分支，那种"全绿"没意义。
- **用例必须来自真实 bug**：每条带 `why` 字段说明守护什么。随手编的用例只让分数好看，退化时不会报警。
- **期望值必须实测**：我写过一条"期望 top1 是语音档案"，红了——查下来是我探测时**手动加了过滤**才拿到那个结果，真实链路里路由推不出语音。写成"觉得应该对"的期望，等于自欺欺人。

### 5. 语料变了，融合权重必须重扫

补进 19,797 块剧情后，hybrid 的 Recall@1 从 80% 掉到 60%，而 dense 单独仍有 80%。查下来是 BM25 那一路被稀释——剧情里角色名高频重复（"阿米娅："出现成千上万次），BM25 靠词频打分，把大量剧情台词顶到前排，挤掉了真正的档案块。

扫描 `W_SPARSE`（同一批探针，只改这一个数）：

| 权重 | Recall@1 | Recall@5 | MRR |
|---|---|---|---|
| 0.7（旧值）| 60% | 100% | 73.7% |
| **0.3（采用）** | **90%** | **100%** | **93.3%** |
| 0（直接去掉）| 80% | **80%** | 80.0% |

最后一行才是重点：归零反而掉 20 个点，说明稀疏路捞回了 dense 漏掉的那部分——**它该被削弱，不该被移除**。0.2 和 0.3 都在最优平台区，取 0.3 更保守，给稀疏路留一点将来补位的余地。

教训：**融合权重不是调一次就永远对**。语料分布一变（新增数据源、改切块策略），权重就得重扫。

### 6. 期望值要跟着数据更新

补剧情之前，"森西和泥岩之间有什么故事"是一条**拒答用例**（期望无共现）。补完之后它变红了——因为两人在联动活动「品尝魔物」里真的对话了。

这不是 bug，是知识库变大后**事实本身变了**。处理方式：把它改造成新能力用例（期望有共现），另找一对真正 0 共现的（史尔特尔 + 泥岩）继续守拒答。

推论：**拒答的正确性依赖于知识库的覆盖范围**。同一个问题，库小的时候答"不知道"是对的；库大了还答"不知道"，那就是漏召回。所以每次扩完数据，拒答用例都要复查一遍。

### 7. 已知局限显式记录，不删掉假装不存在

`凯尔希和博士是什么关系` 目前答不了关系。注意**不是博士没有剧情身份**——他是罗德岛的指挥核心，与凯尔希的旧交本身就是主线挖过的线。真正的原因是数据结构与算法边界的叠加：

1. **不在实体表**：`operators` 表存的是 463 名**可操作干员**，博士不可操作，所以实体匹配器识别不出他——这类问题从路由那步就只拿到"凯尔希"一个实体；
2. **共现信号失效**：就算手动把他加进实体表也不行。"博士"出现在 29% 的剧情页（509/1727），凯尔希出场的页面里 73%（242/333）同时有博士——**"同框"不再说明任何关系**，检索会退化成"凯尔希出场过的所有主线"。对比：泥岩仅出现在 17 页，低频名字的共现才是金子。

这是**有意的设计取舍**，代价记在案。突破需要换机制——对"博士"这类高频主角做白名单，并用专门的关系抽取替代共现——超出本项目当前范围。

### 8. 用户要的不是"总量"，是"花在哪"

满练度材料的第一版回答是一张 34 项的总表，数字全对，但用户看不出来龙门币 81 万里哪部分是精英化、哪部分是模组。于是把汇总升级为**分阶段养成清单**：明细（精英化1/2 → 技能2~7级 → 各技能专精 → 各模组）+ 各大阶段【小计】+ 全阶段【总计】，三层全部由 SQL 算好。

期间两次抓到模型"顺手算数"：一次是在残缺表上自己加总（8+12+15…=70），一次是把相邻两级的卷1×5 合并成 ×10——两次都恰好算对，但**只要留了机会它就会算**，所以连"阶段内合并"也必须下推到 SQL。

顺带核对出一个容易误判的数据事实：技能 3~7 级本来就带按干员区分的额外材料（每个干员一套组合，并非职业统一），与 Wiki 原文逐字核对一致。**"看起来像 bug 的数据"，先核对数据源再下结论。**

补完阶段后还剩一块：把等级从 1 练到上限的经验与龙门币。我以为要去抓，翻本地却发现「干员升级数值」「干员等级上限」「作战记录换算」三个页面**第一次抓全站时就存下来了**，只是从没解析。

这里有个值得记住的分类：**"数据源里没有"和"我有数据但没解析"是两种完全不同的问题**，后者修复成本是前者的百分之一。动手抓之前先 grep 一遍本地，这个项目因此省了一次数小时的抓取。

还有一次返工：把 161 行的清单平铺给模型，它自己压缩成一个总计交差，还漏掉排在表最前面的等级段。**"按阶段分组"在代码里是一次顺序扫描，交给模型就是赌博**——最后改成在 prompt 组装层就分好组（每组一个小标题），模型只负责转述。

## 已知局限

- **"博士"不是可操作干员**，不在实体表；且他出现在 29% 的剧情页，共现信号在他身上失效——涉及博士的关系类问题（如"凯尔希和博士的关系"）答不了。详见上文第 7 节。
- **隐含资料类型推不出**："泥岩在罗德岛适应得怎么样"推不出该查语音档案，只有"台词""语音"这类显式词才触发。
- **生成层答案质量未做自动评判**，只判引用编号是否真实存在（幻觉信号）。答案好不好仍需人工或 LLM-as-judge。
- **单轮问答**，无多轮对话记忆。
- **数据需自行抓取**，仓库不含任何 Wiki 原文。

### 语料覆盖：还有哪些抓下来了但没解析

第一次全站抓取把 19,696 页全存到了本地，但解析器只吃掉了其中一部分。
按页面模板统计，**已解析**的是干员（1,299 页）和剧情（1,727 页）；
下面这些**还在本地躺着**，问到就答不了（会走拒答分支）：

| 类别 | 页数 | 补上后能问什么 |
|---|---|---|
| 敌人 / 敌方单位 | 5,436 | "碎骨的弱点是什么""哪关的敌人会眩晕" |
| 家具 / 基建 | 2,877 | 宿舍氛围、制造站配方 |
| 道具 / 材料 | 1,392 | "扭转醇在哪关掉率最高" |
| 集成战略收藏品 | 859 | "水月与深蓝之树的收藏品效果" |
| 关卡 / 作战 | 220 | 关卡掉落、突袭条件 |
| 危机合约词条 | 43 | 合约效果与等级 |

## 项目结构

```
src/
  prts_client.py      MediaWiki API 客户端
  parser/             wikitext 解析、切块、文档聚合
  store/              SQLite schema / Chroma 向量库
  retriever/          router（规则路由）· hybrid（三路融合）· lexical（BM25）
  generator/          prompt（证据组装）· llm（OpenAI 兼容客户端）
scripts/              01~22 流水线与工具脚本
docs/                 方法论文档（数据质检规范等）
data/                 运行时产物，不入库
```

每一步脚本的开头都写了一段说明，讲清它在 RAG 全景里的位置和为什么这么做——这个项目本身就是按"可教学"的标准写的。
